# 业务逻辑写作规范

本规范是 Skill2 / Skill3 / Skill4 / Skill5 的共同源头。  
用户侧悬浮面板、右侧 PRD 面板、Markdown PRD 中的业务逻辑正文，都必须按本规范生成与展示。

配合阅读：

```txt
.ai/skills/shared/project-context.md
.ai/skills/shared/incremental-scope-mode.md
.ai/skills/LOGIC-WRITING-ADJUSTMENT-PLAN.md
```

增量模式下：只为 Skill0 必审对象（A∪B）撰写或更新 `logicSections`；不对 C 类对象重写既有逻辑。详见 `incremental-scope-mode.md`。

---

## 1. 总原则

1. **先收集业务规则，再归类成一级标题。**  
   标题来自规则归类结果，不是开写前的必填模板。
2. **内容完整，不只写当前前端已实现。**  
   必须覆盖代码已体现、Skill1 已确认、以及合理延伸的边界场景。
3. **一条业务规则只写一次。**  
   禁止同一规则在多个标题下换说法复述。
4. **有规则才开标题，无规则不开标题。**  
   不为结构完整强行补空栏目。
5. **表达短、可验收、产品语言。**  
   不写技术实现，不写空话。

用户可见正文的唯一结构是注册表中的 `logicSections`，不再使用固定的 `display` + `operation` 作为用户正文主结构。

---

## 2. 正确写作顺序

对每个页面对象，必须按下面顺序执行：

```txt
1) 收集规则素材（来源 A + B + C）
2) 整理成一条条可验收的业务规则（此时可不标标题）
3) 按“这条规则在回答什么问题”归类
4) 用归类结果生成一级标题，写入 logicSections
5) 无规则的标题不生成；同一规则只进一个标题
6) 自检：空标题、跨标题重复、只写了代码表面、该延伸未延伸
```

### 2.1 规则来源（三来源）

| 来源 | 含义 | 说明 |
| --- | --- | --- |
| A. 代码已体现 | 当前页面已实现的展示与交互 | 必要，但通常不够 |
| B. Skill1 已确认 | 审核决策里已拍板的业务口径 | 硬约束，优先于猜测 |
| C. 合理延伸 | 基于 A+B，该对象常需补齐、且与已确认口径一致的边界场景 | 如快照不回刷、转班、截止后重批等 |

**明确禁止：** 只根据前端现有样式/按钮，把注释写成「当前代码做了什么」的说明书。

**页面可以很简单，注释可以很完整。**  
例如页面只有日期或切换入口，仍可写出统计口径、生成规则、快照及历史查看规则。

### 2.2 合理延伸边界

要写：

- 与已确认主规则直接相关的边界（时点、纳入/排除、生成触发、快照是否回刷、历史入口行为等）
- 该类字段/模块通常必须定清，否则无法验收的规则

不要写：

- 与 Skill1 已确认口径矛盾的新方案
- 纯技术实现细节（接口名、字段名、组件内部状态、DOM、缓存键等）
- 明确不在本次页面范围的能力

拿不准且影响验收时：回到 Skill1 确认，不假装代码已实现。

## 3. 一级标题：分类词库，不是必填表

标题是「已经写出来的规则，归类后的名字」。

常用候选（有规则才用；可按内容选用更准确的名字）：

- 显示说明
- 操作说明
- 统计口径
- 计算规则
- 数据规则 / 数据来源
- 选取规则
- 排序规则 / 展示顺序
- 状态规则 / 状态定义
- 生成规则
- 快照规则 / 历史数据规则 / 快照及历史报告查看规则
- 异常情况处理
- 以及其他能准确概括该组规则业务性质的自定义标题

归类参考：

- 展示什么、什么状态/条件展示、无数据怎么展示 → **显示说明**
- 用户点击/切换/输入/提交后系统如何响应 → **操作说明**
- 统计谁、统计哪些数据、时间范围、纳入/排除 → **统计口径**
- 公式、映射、差值、累计、去重后才得出结果 → **计算规则**
- 数据来自哪个系统/配置/时点/版本 → **数据规则** 或 **数据来源**
- 先筛哪些候选再决定展示谁 → **选取规则**；先后顺序 → **排序规则** / **展示顺序**
- 状态含义、流转条件 → **状态规则** / **状态定义**
- 何时生成、什么条件触发/不触发 → **生成规则**
- 历史是否冻结、是否回刷、读快照还是实时 → **快照/历史** 类标题
- 空数据、失败、无权限、处理中、重复操作等 → **异常情况处理**

禁止：

- 固定套用「显示说明 + 操作说明」两段式
- 默认再拆「页面展示 / 状态反馈 / 操作规则 / 后续流程 / 异常边界」固定子模板
- 默认使用「后续流程」作兜底筐
- 为凑结构生成空标题或空兜底句（如「无额外权限限制」「本对象仅展示」）

## 4. `logicSections` 写法

```js
logicSections: [
  {
    title: "生成规则",
    items: [
      "学生在当前日报统计周期内满足任一有效行为时，生成当日日报。",
      "当日 24:00 之前不生成或展示当日日报临时结果。"
    ]
  }
]
```

要求：

- `title`：一级标题，产品语言，准确概括本组规则
- `items`：字符串数组；每条一个可验收事实；不要在条目内再手写 `1、`/`1.1` 前缀（由展示层统一编号，或按组输出 `1.1` 风格时保持单层）
- 推荐展示编号：每个一级标题下使用 `1.1`、`1.2`…；禁止多层套娃编号
- `logicSections` 是用户可见业务逻辑的**唯一来源**

## 5. 正例特征

好的结果通常具备：

- 只出现真正有规则的标题
- 统计/生成/快照/异常等按问题分开，不塞进“显示/操作”硬二分
- 含 Skill1 口径与必要延伸，不只描述 UI 表象
- 短句、可验收、不复述

参考风格（不必原文照抄）：

- 学前掌握状态：显示说明 + 数据规则 + 异常情况处理
- 知识点状态：显示说明 + 统计口径 + 掌握度展示通用规则 + 展示顺序
- 再练一次：选取规则 + 展示顺序 + 显示规则 + 操作说明
- 日报生成条件：统计口径 + 生成规则 + 快照及历史报告查看规则

---

## 6. 反例特征（禁止）

- 先摆固定栏目，再往里填
- 同一事实在多个栏目反复出现
- 多层 `1、` 套 `1、`
- 把框选范围、统计口径、生成条件误塞进「状态反馈」
- 只写“页面上有个日期按钮”，不写统计周期、生成触发、快照是否回刷等应有规则

---

## 7. Skill3 / Skill4 / Skill5 渲染规则

悬浮面板、右侧 PRD 面板、Markdown PRD：

1. **只渲染 `logicSections`** 的 `title` + `items`
2. **禁止**二次映射成固定子模板栏目
3. **禁止**自动补空栏目
4. **禁止**对已有条目再套一层编号造成双编号
5. **禁止**把空兜底说明展示给用户
6. 渲染层**不负责重新组织业务逻辑**，只负责呈现 Skill2 已生成的分组

## 8. 质量自检清单

生成或展示前检查：

- [ ] 是否按「收集规则 → 归类 → 开标题」执行，而不是先开标题再填空
- [ ] 是否同时考虑了代码、Skill1 决策、合理延伸
- [ ] 是否存在空标题或空栏目
- [ ] 是否存在跨标题重复
- [ ] 是否只写了 UI 表象而缺少应有业务口径
- [ ] 是否出现技术实现词或空话
- [ ] Skill3/4/5 是否仍在二次套模板（若有，必须去掉）
