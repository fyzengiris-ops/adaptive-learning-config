# 业务逻辑写作调整方案（Skill2–5）

> 状态：已确认并已落地到 Skill2–5 与共享规范。  
> 目标：让 Skill2 生成、Skill3/4 展示、Skill5 归档，达到 GPT 好例那种「问题归类、不啰嗦不重复」的效果；不依赖 Skill6。

---

## 1. 最终目标

用户在悬浮面板 / 右侧 PRD 面板 / Markdown PRD 中看到的业务逻辑，应接近以下风格：

- 一级标题由**真实业务规则归类**产生，不固定套「显示说明 + 操作说明」模板
- 有什么规则写什么标题；没有对应规则就不生成该标题
- **一条业务规则只出现一次**，不在多个栏目换说法复述
- 编号干净（如 `1.1`、`1.2`），无多层 `1、` 套 `1、`
- 内容完整：不只描述当前前端已实现，还包含 Skill1 已确认口径，以及合理延伸的边界场景

**不依赖 Skill6。** 若 Skill2–5 调整到位，Skill6 可不进入主流程。

---

## 2. 核心写作范式（所有改动的总原则）

### 2.1 正确顺序（必须按此执行）

```txt
1) 收集规则素材（三来源 + 合理延伸）
2) 整理成一条条可验收的业务规则（此时可不标标题）
3) 按“这条规则在回答什么问题”归类
4) 用归类结果生成一级标题，并写入 logicSections
5) 无规则的标题不生成；同一规则只进一个标题
```

### 2.2 「收集规则素材」不等于「只抽前端代码」

对每个页面对象，规则来源至少包括：

| 来源 | 含义 | 说明 |
| --- | --- | --- |
| A. 代码已体现 | 当前页面已实现的展示与交互 | 必要，但通常不够 |
| B. Skill1 已确认 | 审核决策里已拍板的业务口径 | 硬约束，优先于猜测 |
| C. 合理延伸 | 基于 A+B，该对象常需补齐、且与已确认口径一致的边界场景 | 如快照不回刷、转班不改历史排名、截止后重批不进当日/历史日报等 |

**明确禁止：** 只根据前端现有样式/按钮，把注释写成「当前代码做了什么」的说明书。

**页面可以很简单，注释可以很完整。**  
例如页面只有日期或切换入口，仍可写出统计口径、生成规则、快照及历史查看规则等（参考「日报生成条件」好例）。

### 2.3 合理延伸的边界

要写：

- 与已确认主规则直接相关的边界（时点、纳入/排除、生成触发、快照是否回刷、历史入口行为等）
- 该类字段/模块通常必须定清，否则无法验收的规则

不要写：

- 与 Skill1 已确认口径矛盾的新方案
- 纯技术实现细节（接口名、字段名、组件内部状态等）
- 明确不在本次页面范围的能力

拿不准且影响验收时：回到 Skill1 确认，不假装代码已实现。

### 2.4 一级标题：分类词库，不是开写前的必填表

标题来自「规则归类后的组名」，不是「还没写规则就先猜要哪些标题」。

常用候选（有规则才用，可按内容选用更准确的名字）：

- 显示说明
- 操作说明
- 统计口径
- 计算规则
- 数据规则 / 数据来源
- 选取规则
- 排序规则 / 展示顺序
- 状态规则 / 状态定义
- 生成规则
- 快照规则 / 历史数据规则 / 快照及历史报告查看规则
- 异常情况处理
- 以及其他能准确概括该组规则业务性质的自定义标题

禁止：

- 固定套用「显示说明 + 操作说明」两段式
- 为结构完整强行补空标题
- 默认使用「后续流程」「页面展示 / 状态反馈 / 操作规则 / 异常边界」这类旧固定子模板去扩写
- 同一规则在多个标题下重复

### 2.5 编号与表达

- 一级标题下用 `1.1`、`1.2`…（或组内连续短编号）
- 一条只讲一个可验收事实
- 不写「方便用户理解」类空话
- 不写多层编号套娃

## 3. 正例 / 反例（改 Skill 时写入规范）

### 3.1 正例特征（对齐 GPT 好例）

- 学前掌握状态：显示说明 + 数据规则 + 异常情况处理（无操作则无操作说明）
- 知识点状态模块：显示说明 + 统计口径 + 掌握度展示通用规则 + 展示顺序
- 再练一次：选取规则 + 展示顺序 + 显示规则 + 操作说明
- 日报生成条件：统计口径 + 生成规则 + 快照及历史报告查看规则（含转班、重批、历史跳转等延伸）

### 3.2 反例特征（对齐 Codex 差例，明确禁止）

- 先摆固定栏目，再往里填
- 「题目+答案不同文件不自动切题」等同一事实在状态反馈、操作规则、异常边界反复出现
- 「未识别题号不得推测」在显示/状态/操作/异常四处复述
- 多层 `1、` 套 `1、`
- 把框选范围、自动切题目标误塞进「状态反馈」

## 4. 各文件具体怎么改

### 4.1 `shared/logic-writing-spec.md`（共同源头，优先重写）

整份改为上述范式，替换当前「必须显示说明/操作说明 + 固定检查框架 + 固定产品化子标题」导向。

必须写清：

1. 三来源收集 + 合理延伸  
2. 先规则后归类  
3. 标题词库与命名规则  
4. 一条事实只写一次  
5. 编号与表达质量要求  
6. 正例/反例  
7. Skill3/4/5 只渲染归类结果，不得二次套模板

### 4.2 Skill2 + `registry-field-spec.md`（生成端，决定质量）

#### 数据结构

新增用户可见逻辑的唯一来源字段，例如：

```js
logicSections: [
  {
    title: "生成规则",
    items: [
      "学生在当前日报统计周期内满足任一有效行为时，生成当日日报。",
      "..."
    ]
  }
]
```

约定：

- `logicSections` = 悬浮面板 / 右侧 PRD / Markdown PRD 的正文来源
- 旧的 `display` / `operation` / `permission` / `dataFlow` / `exceptions`：
  - 方案：**不再作为用户正文主结构**；可删除，或仅保留极少量内部追溯字段且默认不渲染
  - 推荐：以 `logicSections` 为主，避免两套正文并存导致再次分叉

#### Skill2 流程改写

在生成每条需求正文时强制：

1. 收集 A/B/C 规则素材  
2. 写成原子业务规则列表  
3. 归类 → 生成 `logicSections`  
4. 自检：空标题、跨标题重复、只写了代码表面、该延伸未延伸  

摘要输出可增加：本条使用了哪些一级标题、是否含 Skill1 决策与延伸规则。

### 4.3 Skill3（悬浮面板）

- 只按 `logicSections` 渲染：标题 + 条目
- 禁止二次映射为「页面展示 / 状态反馈 / 操作规则 / 后续流程」
- 禁止自动补空栏目
- 禁止对已有条目再套一层编号
- 角标、锚点、拖拽等交互职责不变

### 4.4 Skill4（右侧 PRD 面板）

- 与 Skill3 同源，只渲染 `logicSections`
- 明确：**渲染层不重新组织业务逻辑**
- `activate`、分栏、高亮、与角标同步等能力不变

### 4.5 Skill5 + PRD 模板

- 每条需求的业务逻辑章节按 `logicSections` 原样输出 `#### 标题` + 条目
- 取消强制「显示说明 + 操作说明」两段式
- 只有一个分组就只输出一个分组
- 范围边界、验收标准、来源追溯等其他章节结构可保留

### 4.6 明确不改 / 弱化

| 项 | 处理 |
| --- | --- |
| Skill1 | 不改主流程；它继续负责确认关键口径，供 Skill2 作为来源 B |
| Skill6 | 本次不作为主改对象；主路径不依赖它 |
| 路由/锚点/`activate`/角标位置 | 不因本次写作调整而改语义 |
