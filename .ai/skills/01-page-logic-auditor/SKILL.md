# 页面逻辑审核 Skill

## 目标

从产品设计者和测试者两个视角审核当前前端页面。不要直接改页面，也不要直接生成最终 PRD。核心目标是发现**必审对象**上尚未明确的业务逻辑、边界、异常与交互规则，并整理成可快速决策的选项。

执行前必须先读：

```txt
.ai/skills/shared/project-context.md
.ai/skills/shared/incremental-scope-mode.md
```

并遵守与 Skill0 的衔接门禁：**没有已确认的对象清单，不得开始本 Skill 的决策题输出。**

## 与 Skill0 的衔接门禁（必须）

完整顺序：

```txt
Skill0 对象清单（已确认）→ Skill1 本审核 → Skill2 …
```

1. 开始前检查是否存在已确认清单：

```txt
docs/prd-workflow/inventories/<页面或流程>.inventory.md
```

2. 若清单不存在，或文件中「清单状态」不是已确认：
   - 不要输出 `1A2C3D` 待确认问题；
   - 告知用户需先执行 Skill0（`.ai/skills/00-page-object-inventory/SKILL.md`）；
   - 询问是否现在开始 Skill0。
3. 若清单已确认：
   - **只对清单中的「必审对象」**出待确认问题；
   - 「可跳过对象」默认不审，除非用户在本轮明确要求加入；
   - 若清单为 **增量模式**：必审 = A∪B；对 C **不得**出决策题，也不得建议改写其既有业务口径；最多可在内部备注「观察」，不进入决策文件；
   - 审核中若发现清单外仍有**与本次变更相关的连带对象**：先暂停扩审，回到 Skill0 补 B 类并经用户确认后，再继续；
   - 不得借「顺便优化」扩大到 C 类整页重审。
4. 决策记录仍只写用户已确认的业务口径；清单文件本身不是决策，不能替代 `decisions/*.decision.md`。

## 必须遵循的流程

1. 确认页面/流程范围；未知则先问。
2. 确认前提信息；无额外前提可回复「无额外前提」。
3. 检查 Skill0 已确认清单；不存在则停在门禁，不进入决策题。
4. 读取清单中的「审核模式」。若为增量，复述：变更摘要 + 必审数量（A/B）+ 「不对 C 重审」。
5. 按 `project-context.md` 的读码约定打开相关文件（技术栈以该文件为准，不要假设固定为静态 HTML 或固定为某一框架）。
6. 仅针对必审对象定位 UI 与相关状态交互（字段、文案、按钮、弹窗、Tab、列表、空/载/成/败/禁用等）。
7. 同时扮演产品设计者与测试者；只输出影响业务逻辑、PRD、验收或实现的问题。
8. 首次结果用“首次输出格式”；用户 `1A2C3D` / 自定义 / 疑问按后文规则处理。
9. 本轮问题均有明确决策后，用“决策确认格式”回显；用户确认后再写入 decision 文件。
10. 增量模式下，decision 文件须注明审核模式与变更摘要，且已确认决策仅覆盖 A∪B。

## 前置信息检查

开始审核前必须检查：

1. 页面名称或页面范围（以用户指定与 `project-context.md` 对照表为准）
2. 页面前提信息（允许「无额外前提」）
3. Skill0 已确认清单（含模式：全页 / 增量）

如果缺少信息，按下面方式提问：

```md
我需要先确认以下信息，再开始审核：

1. 页面名称/页面范围：<已知则写出；未知请补充>
2. 页面前提信息：<已知则写出；未知请补充，允许「无额外前提」>
3. Skill0 清单：<若缺失，询问是否现在开始 Skill0>
```

不要在缺少必要信息时直接开始审核。

## 首次输出格式

首次审核结果必须用中文，并严格使用下面的一级结构：

```md
一、页面名称
<页面名称或流程名称>（<路由或主要文件路径>）

二、待确认问题
**1、<字段/文案/按钮/某区域>：<对象名称>**

**问题描述：**<说明当前代码已实现什么、还缺少什么业务情景、为什么需要确认。>

**建议方案：**
A. <方案A，写清采用后的业务含义>
B. <方案B，写清采用后的业务含义>
C. <方案C，写清采用后的业务含义>

---

**2、<字段/文案/按钮/某区域>：<对象名称>**

**问题描述：**...

**建议方案：**
A. ...
B. ...
C. ...

你可以直接回复类似：1A2C3B
```

首次输出规则：

- 编号从 `1` 开始连续递增。
- 每个问题只能对应一个字段、文案、按钮、区域或逻辑对象。
- 编号对象行必须加粗，例如：`**1、按钮：确认按钮**`。
- 问题描述标题必须写成 `**问题描述：**`，不要写成“关于【对象】的问题描述”。
- 建议方案标题必须写成 `**建议方案：**`。
- 编号对象行、问题描述、建议方案之间各空一行。
- 每个编号问题之间用 `---` 分割；如果问题很少，也可以用两行空行分隔，但优先用 `---`。
- 每个问题建议提供 2-4 个互斥方案。只有确实需要时才提供更多。
- 同一个编号下的所有建议方案必须回答同一个决策维度，方案之间必须可比较、可互斥；不要把“支持范围”“实现方式”“入口策略”“异常处理口径”等不同维度混在同一组选项里。如果发现多个维度都需要确认，必须拆成多个编号问题。
- 建议方案必须完整到可以直接沉淀为 PRD 或开发需求。凡是方案里包含提示、报错、警告、空状态、失败状态、禁用状态、二次确认、拦截或恢复动作，必须同时写清触发条件和具体提示文案，不要只写“给提示”“显示错误”“弹窗确认”等笼统表述。
- 如果提示文案本身还不确定，必须把文案作为该编号下的可选方案，或拆成独立编号让用户确认。
- 只有当“不处理/保持现状”本身是合理产品决策时，才加入这个选项。
- 不要输出冗长背景、代码逐行讲解或实现计划。
- 如果问题太多，优先输出 P0/P1 问题，并说明页面可以分批审核。
- 不要把多个无关决策混在同一个编号问题里。

## 用户决策回复解析

当用户回复类似 `1A2C3D` 时，按下面规则解析：

- `1A` 表示第 1 个问题选择 A 方案。
- `2C` 表示第 2 个问题选择 C 方案。
- `3D` 表示第 3 个问题选择 D 方案。

用户回复可能不是纯编号选项，必须支持下面情况：

1. 标准选项  
   示例：`1A2C3D`。按编号和选项字母记录。

2. 自定义方案  
   示例：`1A2C3【改成上传前先让用户选择资料类型，再进入导入弹窗】5B`。  
   对第 3 个问题记录为“自定义方案”，并完整保留用户输入的文字，不要强行改写成已有 A/B/C/D。

3. 表示没看懂或提出疑问  
   示例：`1A2C3D4【我没看懂这个问题，是不是指关闭弹窗后数据会丢失？】5A7D`。  
   对第 4 个问题不要记录决策，按“疑问回复处理规则”先解释，等用户补充第 4 个问题的决策后，再统一回显完整决策结果。

4. 混合回复  
   同一条回复里可以同时包含标准选项、自定义方案和疑问。必须先记录已明确的决策，保留未决问题，不能丢失用户已经选择的其他编号。

如果用户回复里有无效编号、无效选项或无法判断的内容，只询问需要修正的那几项，不要重新输出全部审核内容。

## 自定义方案处理规则

当用户没有选择 A/B/C/D，而是对某个编号输入自己的解决方案时：

- 将该编号的决策标记为“自定义方案”。
- 原样保留用户输入的核心方案文字。
- 可以在决策确认时做轻微结构化整理，但不得改变用户方案含义。
- 写入决策记录时，`决策` 写为“自定义方案”，`结论` 写用户自定义方案的完整业务含义。
- 如果用户自定义方案里同时包含疑问或条件，先确认歧义，不要直接写入最终决策。

自定义方案在决策确认格式中这样展示：

```md
**3、按钮：确认按钮**

**决策结果：**自定义方案，<用户输入方案的完整业务含义。>
```

## 疑问回复处理规则

当用户对某些编号表示没看懂、有疑问、反问含义、要求解释时：

1. 先暂存其他已经明确的编号决策。
2. 不要输出完整决策结果。
3. 只针对用户有疑问的编号进行扩展说明。
4. 扩展说明后，重新给出该编号可决策的方案；可以沿用原 A/B/C/D，也可以根据用户疑问补充更清晰的新方案。
5. 明确告诉用户只需要继续回复未决编号，例如：`请继续回复：4A`。
6. 用户补齐未决编号后，再把之前暂存的明确决策和新补齐的决策合并，使用“决策确认格式”统一输出完整决策结果。

疑问回复格式如下：

```md
一、已记录决策
已先记录：1A、2C、3D、5A、7D。

二、需补充说明的问题
**4、<字段/文案/按钮/某区域>：<对象名称>**

**扩展说明：**<用更直白的话解释这个问题在问什么、为什么会影响业务逻辑或测试验收。>

**重新提供建议方案：**
A. <方案A>
B. <方案B>
C. <方案C>

你可以继续回复：4A
```

## 决策确认格式

解析用户选择后，必须用中文回显，并严格使用下面结构：

```md
一、页面名称
<页面名称或流程名称>（<路由或主要文件路径>）

二、决策结果
**1、<字段/文案/按钮/某区域>：<对象名称>**

**决策结果：**<选择的方案字母>，<该方案的完整业务含义。>

---

**2、<字段/文案/按钮/某区域>：<对象名称>**

**决策结果：**<选择的方案字母>，<该方案的完整业务含义。>

请确认以上决策是否正确。确认后我会把它沉淀为页面决策记录。
```

在用户确认前，不要写入决策记录文件。

## 决策记录文件

用户确认决策结果后，创建或更新：

```txt
docs/prd-workflow/decisions/<页面或流程>.decision.md
```

文件结构如下：

```md
# <页面名称或流程名称> 决策记录

## 页面范围
- 页面/流程：<名称>
- 路由：<以 project-context 为准>
- 相关代码文件：
  - <file>
- 审核模式：全页 | 增量
- 本次变更摘要：<增量时必填；全页可写「整页」>

## 已确认决策
1. <字段/文案/按钮/某区域>：<对象名称>
   - 影响类型：A | B | （全页可省略）
   - 决策：<选择的方案字母>
   - 结论：<完整业务含义>
   - 影响范围：<页面显示、操作、权限、数据流转、异常处理等>

## 明确不重审（增量 C 类，可选）
- <对象> — <不重审原因>

## 暂不处理
- <如有>

## 待后续确认
- <如有>
```

决策记录是后续“需求注册表” skill 的输入材料。文件必须简洁、具体、可追溯，不要写入未确认建议。增量模式下不得把 C 类对象的新口径写进「已确认决策」。

## 审核关注点

输出待确认问题前，至少检查下面维度：

- 入口：谁能看到入口、什么时候可点击、关闭后回到哪里。
- 文案：按钮文案、空状态文案、提示文案、状态文案是否和实际行为一致。
- 状态：加载、空、成功、失败、禁用、部分成功、恢复、重复操作状态是否完整。
- 权限：不同角色、数据归属、受限操作是否需要明确规则。
- 数据流转：数据从哪里来、保存到哪里、跨页面跳转/刷新/关闭弹窗后如何处理。
- 异常：非法输入、缺少输入、接口失败、请求超时、重复提交、中断流程、不支持的文件或数据。
- 隐藏交互：弹窗、悬浮面板、Tab、步骤、抽屉、Popover、hover 后才出现的操作。
- 校验：当前代码是否阻止了不可能或高风险操作。
- 恢复：用户是否能取消、重试、恢复、重新上传、继续流程，并避免数据丢失。

## 输出约束

- 面向用户的输出必须以决策为中心。
- 不要把所有小观察都塞给用户。
- 使用页面上的具体对象名称。
- 不要提出“是否优化体验”这类空泛问题。
- 每个选项都必须能成为后续 PRD 或实现决策。
- 对提示、报错、拦截、禁用、空状态、失败状态、确认弹窗等异常或状态处理，必须输出可落地的文案和触发条件；没有具体文案的方案不算完整方案。
- 除文件路径、代码标识、字段名、命令名等必要内容外，尽量使用中文。
- 页面对象与命名以当前 `project-context.md` 与用户指定范围为准；不要默认套用其他产品线业务。
- 增量模式：只审 A∪B；发现新连带先回 Skill0；不对 C 改写既有逻辑。
- 忽略仓库历史整页 PRD 模板，除非用户当轮要求沿用（见 `incremental-scope-mode.md`）。
